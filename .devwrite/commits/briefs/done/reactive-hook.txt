subject: one line, under 70 chars. It is about a tool being able to watch an ordinary
         application — not about "exposing" or "adding" anything.
body:    first paragraph is the reason, in the past tense: what was wrong before. Then one
         short paragraph per note below, in that order. No closing summary.

files:  packages/reactive/src/lib/signal/graph/observe.ts (new), observe.spec.ts (new),
        core.ts, runtime.ts, compat.ts, state.ts, signal/index.ts, README.md
what:   observeReactiveNodes: created / ran / disposed / moved, each handed the core node.
why:    createReactor in @fluixi/devtools hands out its own primitives, so it only ever saw
        code written against it. An app that imports signal normally was invisible to it.
notes, one per paragraph:
  - nothing is wrapped and no read is intercepted. A source already keeps its observers and
    a consumer its sources, so a watcher reads the edges rather than rebuilding them.
  - the observer sits on G, the globalThis-backed state, for the reason everything else
    there does: two copies of the module in one bundle still have one observer.
  - a report carries the whole chain of running computations. The innermost is usually a
    render effect, which no graph draws, so a row added to a list would arrive with nothing
    to attach it to.
  - render effects are reported and flagged as plumbing — one per dom binding is not worth
    drawing, but a node made inside one still has to find the component that caused it.
  - signals and memos say when they go, through their owner. Without that a list rebuilt
    without a key left a node per row per update in a watcher's graph.
verify: 219 tests in the package, seven of them new against a watcher. Unwatched, a node
        creation costs one property read.
