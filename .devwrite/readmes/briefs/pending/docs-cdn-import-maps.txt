package:  docs — a new section for content/v1/en/cdn.md
audience: someone loading Fluixi in a page with no bundler, who has read the
          global-build sections above and wants real modules instead
one-line: the import-map path, alongside the IIFE globals already documented
measured: the minimum map is 15 entries; templates adds 3; full is 19
verified: both blocks below were run in a browser against the published packages
do-not-claim: that an import map can be referenced by url. `<script type="importmap"
          src="...">` was specified and never shipped. Do not show it.
          do not say the globals are deprecated. Both paths are supported, and a
          global stays smaller for a single-file drop-in.
structure: it is inserted before the "Version pinning" section. Heading level 2,
  titled "Bare imports — `@fluixi/cdn`". Then, in order:
  1. why this rather than a global: a global puts one object on `window`, and
     `reactive`, `core` and `fluixi` all claim the same name, so only one may be
     loaded. With a map the page writes the same `import` statements a built app
     writes, and loads only the subpaths it touches. A browser resolves a bare
     specifier only through a map and never reads package.json, so every
     transitive subpath has to be listed; @fluixi/cdn is that list, generated per
     release and pinned to it.
  2. the three maps, one line each: min (15 entries — core, dom, utils and the
     graph behind them), templates (adds 3, for compiling html`` in the page),
     full (19, everything a browser can use). Each ships as .json to read or
     paste and .js to load.
  3. say the .js installs the map, and has to come before the first module
     script, because a map added after one has begun loading is ignored. Then
     this block VERBATIM:
```html
<div id="app"></div>
<script src="https://unpkg.com/@fluixi/cdn/dist/min.js"></script>
<script type="module">
  import { render, signal, effect } from '@fluixi/core';

  function Counter() {
    const n = signal(0);
    const button = document.createElement('button');
    button.addEventListener('click', () => n.set(n() + 1));
    effect(() => { button.textContent = `count: ${n()}`; });
    return button;
  }

  render(() => Counter(), document.getElementById('app'));
</script>
```
  4. say that html`` needs the template runtime, and that the `html` re-exported
     from @fluixi/core is the tag the compiler replaces at build time — calling
     it in the page throws. Then this block VERBATIM:
```html
<div id="app"></div>
<script src="https://unpkg.com/@fluixi/cdn/dist/full.js"></script>
<script type="module">
  import { render, signal } from '@fluixi/core';
  import { html } from '@fluixi/template-runtime';

  function Counter() {
    const n = signal(0);
    return html`<button @click=${() => n.set(n() + 1)}>count: ${n}</button>`;
  }

  render(() => Counter(), document.getElementById('app'));
</script>
```
  5. close with two short facts: the .json is there for a page that would rather
     hold the map in its own markup; and several maps in one page need Chromium
     133 or newer, which is why full exists as one file. @fluixi-ui/cdn carries
     the same thing for the component library and composes with these, since
     neither repeats the other's entries.
